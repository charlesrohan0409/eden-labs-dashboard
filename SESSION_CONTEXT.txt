2. TECH STACK & ARCHITECTURE
================================================================================
- Vite 8 + React 19, Tailwind 3 (warm neutral canvas + emerald accent design system).
- No backend database yet. All app data (clients, posts, invoices, tasks, etc.) lives in
  ONE big JSON object in the browser's localStorage, key "eden-labs-v1-data". Loaded/saved
  via src/hooks/useAppData.js. This was flagged early as a real risk (see §8) — a Supabase
  migration was the ORIGINAL plan's Step 3 but got paused indefinitely when Charles said he
  wanted to keep adding features to the artifact-derived app first. It has NOT been revisited
  since — still pure localStorage, still single-browser, still no auth beyond a client-portal
  PIN and an owner passcode env var.
- Server-side secrets pattern (used for EVERY third-party API key — this is the core
  architectural decision of this whole session, repeat it for anything new):
    - api/_handlers.js holds the actual logic for every /api/* route as a plain async
      function (body) => ({status, body}). Secrets are read via process.env HERE ONLY.
    - api/<name>.js files are thin Vercel serverless-function wrappers around each handler
      (this is what Vercel actually deploys/serves in production).
    - vite.config.js has a custom Vite plugin (apiDevServer) that mounts the exact same
      handlers as Express-style middleware during `npm run dev`, by importing ROUTES from
      _handlers.js and looping over them. This means dev and prod run IDENTICAL logic — no
      separate dev-only mock.
    - The BROWSER NEVER calls a third-party API directly. It always calls same-origin
      /api/buffer, /api/fathom, /api/calendar, /api/send-email. This solves two problems at
      once: (a) secrets never reach client JS / never get bundled by Vite (no VITE_ prefix
      on any of them, which matters because Vite inlines every VITE_*-prefixed var into the
      client bundle at build time — anything without that prefix stays server/Node-only),
      and (b) most of these providers don't set CORS headers for browser calls anyway, so
      direct calls would just fail.
    - src/lib/<name>.js files are the CLIENT-side helpers — thin fetch() wrappers around
      /api/<name> that the React components actually import and call.
  When asked to add a new integration, replicate this exact pattern. Do not put a raw API
  key in a VITE_ var, do not fetch() a third-party API directly from a component.

- .env.local holds all real secrets, is gitignored (confirmed). .env.example documents every
  var with no real values, safe to commit. Current vars (see §5 for status of each):
    VITE_OWNER_PASSCODE   (client-side deliberately — gates the "End contract" dialog, a
                            speed bump not real security, replaced when real auth exists)
    BUFFER_API_KEY        (SET — real key, working, verified against live account)
    RESEND_API_KEY        (empty — user has not gotten a key yet)
    RESEND_FROM           (empty — optional, falls back to Resend's shared sender)
    GOOGLE_CALENDAR_ICAL_URL  (empty — user has key ready, about to paste in)
    FATHOM_API_KEY        (empty — user has key ready, about to paste in)

ARCHITECTURE DECISION — did NOT do a full relational rewrite.
  The app's data model stayed exactly what it was: one big JSON document
  (clients, posts, tasks, invoices, etc.) — same shape components already
  expect. That document now lives in ONE ROW in Supabase (table `app_data`,
  column `data jsonb`) instead of localStorage. This kept the diff small and
  low-risk: every page component is UNCHANGED, `useAppData.js`'s `actions`
  API is UNCHANGED in shape, only the persistence layer underneath moved.
  Full per-table relational schema + RLS-by-user is a real future upgrade if
  team access needs row-level granularity later — not needed for "one owner
  + N clients", which is what exists today.

  Browser NEVER talks to Supabase directly (same rule as Buffer/Resend/
  Fathom — see §2). Every table has RLS enabled with ZERO policies, so even
  a leaked anon/publishable key grants nothing. Only the server-side
  service_role key (in api/_supabaseAdmin.js, read from
  SUPABASE_SERVICE_ROLE_KEY, never VITE_-prefixed) can touch these tables,
  and that key only ever runs inside /api/* handlers.

SCHEMA (applied via mcp Supabase `apply_migration`, name "eden_labs_init")
  app_data            — id=1 singleton, data jsonb (the whole blob), updated_at
  owner_auth          — id=1 singleton, pin_hash, pin_salt (scrypt, see below)
  client_credentials  — client_id (text, matches the id inside the blob's
                         clients[]), pin_hash, pin_salt
  team_members        — id uuid, email, name, role, pin_hash, pin_salt,
                         active, created_at. CREATED BUT NOT WIRED to any UI

                         Charles asked for. Next session: build an owner-side

AUTH DESIGN — self-issued signed session tokens, NOT Supabase Auth.
  PINs are hashed with Node's built-in crypto.scryptSync (salted, 64-byte
  key) — see api/_crypto.js (hashPin/verifyPin/genSalt). Never compared in
  plaintext, never sent to the browser.
  A correct PIN gets a signed token: base64url(JSON payload).base64url(HMAC-
  SHA256 signature), signed with SESSION_SECRET (server-only env var, 32
  random bytes hex). Payload is `{ role: "owner" }` or
  `{ role: "client", clientId }` + iat/exp. 30-day TTL — "log in once, use
  from any device" was an explicit requirement. verifyToken() checks the
  HMAC (timing-safe) and expiry; no DB-backed session table, nothing to
  garbage collect, trivially revocable by rotating SESSION_SECRET (logs
  everyone out at once — noted in .env.local comment).
  Chose this over real Supabase Auth sessions because the app has exactly
  two roles today (owner, per-client) and this reuses the exact "server-only
  secret, /api/* proxy" pattern already established for Buffer/Resend/
  Fathom — one mental model for the whole codebase instead of two.

THE BIG ONE: the Vercel/Supabase bandwidth blowout was an INFINITE REFETCH
LOOP, not payload size. (Charles pushed back on an incomplete first answer —
he was right to.)
--------------------------------------------------------------------------------
  Symptom: Vercel paused the WHOLE account (32GB Fast Origin Transfer),
  Supabase 15GB egress, and a recurring red "Failed to fetch" banner.

  First (incomplete) diagnosis: the app_data blob was ~981KB, 97% of it
  base64 client photos inlined in the JSON. That WAS real and was fixed (see
  Storage migration below) — but it does not explain 15GB/32GB on its own.
  Do not stop at a plausible cause; check request VOLUME too.

  ACTUAL ROOT CAUSE (App.jsx + useOwnerAuth.js):
    useOwnerAuth() returned a fresh object literal every render. App.jsx did
      useCallback(() => ownerAuth.logout(), [ownerAuth])   // whole object!
    so that callback got a new identity every render. useAppData's fetch
    effect depends on that callback => refetch on EVERY render, forever:
      setData -> re-render -> new ownerAuth object -> new callback ->
      effect deps changed -> refetch -> setData -> ...
    No user interaction required. Ran the entire time a tab was open.

  MEASURED, both directions (reverted the fix to confirm, then re-applied):
    before: 87 requests to /api/data in 22s idle (~4/sec)
    after:  0 requests in 42s idle
  Supabase edge logs corroborated: 4,415 GET /rest/v1/app_data in 24h,
  4,317 of them inside ONE hour, on a single-owner app nobody was touching.

  FIX (commit ee83f71), deliberately belt-and-suspenders since either alone
  would stop it and this class of bug is silent and expensive:
    - App.jsx depends on [ownerAuth.logout] (stable), not [ownerAuth].
    - useOwnerAuth memoizes its return value with useMemo.
  Audited siblings: usePortalData already passes a stable [] callback;
  useBufferPerformance + useGoogleCalendar use module-level dedup caches with
  stable deps. No polling anywhere in the codebase (verified: zero
  setInterval in src/).

  NOT RECONCILED: why Vercel says 32GB but Supabase says 15GB. Per GET they
  should be roughly 1:1 (Supabase->Vercel, then Vercel->browser). Could be
  different billing windows, or Vercel counting static assets/request bodies.
  Claude had no access to Vercel's per-route breakdown. If Charles opens
  Vercel's usage page, that gap can finally be closed — ASK FOR IT.

  A recurring task REUSES THE SAME ROW. It flips done=false and slides
  dueDate to the new periodStart. It does NOT create one row per occurrence.
  Therefore THERE ARE NO FUTURE TASK ROWS and you must not create any —
  generated instances would double-count against the source row and be
  regenerated on every server read. "Upcoming" is a DERIVED view; see
  nextOccurrenceFor() added in Phase 2.

  Delivery KPIs gained cadence/periodStart too. seed.js sets the LinkedIn
  "Posts per week" default metric to cadence:"weekly".
